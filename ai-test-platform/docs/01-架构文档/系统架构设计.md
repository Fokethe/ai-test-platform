## 执行摘要

### 项目定位

AI Test Platform 是一款基于人工智能的智能测试管理平台，通过 LLM 和 RAG 技术实现测试用例的智能生成、管理和执行。

### 核心价值

- **智能生成**: 基于需求文档自动生成高质量测试用例
- **知识沉淀**: 通过 RAG 技术复用历史测试经验
- **全链路管理**: 覆盖需求 → 用例 → 执行 → 缺陷的完整测试生命周期
- **协作集成**: 支持飞书/钉钉等协作平台集成（规划中）

### 技术栈总览

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| **前端** | Next.js 16 + React 19 + TypeScript | SSR/SSG 支持，现代化 React 特性 |
| **UI 组件** | shadcn/ui + Tailwind CSS | 统一设计系统，快速开发 |
| **状态管理** | React Hooks + Context | 轻量级状态管理 |
| **后端** | Next.js API Routes | 一体化全栈框架 |
| **认证** | NextAuth.js v4 | 支持多种认证方式 |
| **数据库** | Prisma ORM + SQLite(Dev)/PostgreSQL(Prod) | 类型安全的数据库操作 |
| **AI 框架** | LangChain + LangGraph | AI Agent 编排与工具链 |
| **向量数据库** | ChromaDB / pgvector | RAG 知识库支持 |
| **测试执行** | Playwright | 自动化测试执行引擎 |

### 架构分层说明

#### 1. 用户交互层
- **技术栈**: Next.js 16 App Router + React 19 + TypeScript
- **UI 框架**: shadcn/ui + Tailwind CSS
- **核心页面**:
  - 仪表盘 (/dashboard): 数据概览和快捷入口
  - 测试中心 (/tests): 测试用例/套件管理 + AI 生成
  - 执行中心 (/runs): 测试执行历史和定时任务
  - 质量看板 (/quality): Bug 管理和质量报告
  - 资产库 (/assets): 知识库和页面资产管理
  - 集成 (/integrations): Webhook 和第三方集成

#### 2. API 网关层
- **技术栈**: Next.js API Routes
- **认证**: NextAuth.js v4 (JWT + Session 策略)
- **核心 API**:
  - `/api/tests`: 测试管理
  - `/api/runs`: 执行管理
  - `/api/issues`: 问题管理
  - `/api/assets`: 资产管理
  - `/api/integrations`: 集成管理
  - `/api/ai/*`: AI 生成相关

#### 3. AI 编排层（核心差异化）
- **当前状态**: 独立 Agents，直接调用
- **目标状态**: LangGraph 编排工作流
- **核心组件**:
  - **DocumentParser**: 文档解析（支持 TXT/MD/PDF/DOCX）
  - **RequirementParser**: 需求解析（功能点提取、规则识别）
  - **TestCaseGenerator**: 用例生成（AI + RAG 增强）
  - **RAG Retrieval**: 相似用例检索
  - **ModelManager**: 多模型路由和管理

#### 4. MCP 工具层（规划中）
- **设计目标**: 标准化工具接口，支持外部集成
- **规划工具**:
  - 文档解析工具: PDF/DOCX/OCR
  - 测试技术工具: 等价类/边界值/错误推测
  - 协作集成工具: Jira/TestRail/飞书/钉钉

#### 5. 数据持久层
- **技术栈**: Prisma ORM + SQLite(开发) / PostgreSQL(生产)
- **数据库设计**: 详见 [数据模型设计](#数据模型设计) 章节

// 工作流定义
const workflow = new StateGraph(AgentState)
  .addNode('document_parser', documentParserNode)
  .addNode('requirement_analyzer', requirementAnalyzerNode)
  .addNode('feature_decomposer', featureDecomposerNode)
  .addNode('rag_retriever', ragRetrieverNode)
  .addNode('test_generator', testGeneratorNode)
  .addNode('human_review', humanReviewNode)
  .addEdge(START, 'document_parser')
  .addEdge('document_parser', 'requirement_analyzer')
  .addEdge('requirement_analyzer', 'feature_decomposer')
  .addEdge('feature_decomposer', 'rag_retriever')
  .addEdge('rag_retriever', 'test_generator')

## 技术决策记录

### 决策 1: 为什么选择 LangGraph 编排

**背景**: 当前 Agents 是独立调用的，无法处理复杂的多阶段依赖

**决策**: 引入 LangGraph 作为 AI 编排层

**理由**:
- 支持状态流转和条件分支
- 内置人工审核点（HITL）
- 可视化的工作流定义
- 与 LangChain 生态兼容

**替代方案**:
- 自研工作流引擎（成本高）
- 使用 Temporal（重量级）
- 保持现状（无法满足复杂场景）

### 决策 2: MCP 工具层设计

**背景**: 需要标准化的工具接口，支持外部系统集成

**决策**: 自研 MCP 简化版，而非使用官方 SDK

**理由**:
- 当前需求相对简单，官方 SDK 过于复杂
- 自研可控性高，易于定制
- 渐进式演进，未来可迁移到标准 MCP

**规划工具**:
- 文档解析工具 (pdf-parse, mammoth, OCR)
- 测试技术工具 (等价类, 边界值, 场景法)
- 协作集成工具 (Jira, TestRail, 飞书, 钉钉)

### 决策 3: RAG 实现方案

**背景**: 需要复用历史测试经验来提升 AI 生成质量

**决策**: ChromaDB + OpenAI Embeddings

**理由**:
- ChromaDB 轻量，易于本地部署
- OpenAI text-embedding-3-small 性价比高
- 未来可迁移到 pgvector 统一存储

**替代方案**:
- Pinecone（云端，成本较高）
- Weaviate（功能丰富但复杂）
- pgvector（计划中，统一存储）

### 决策 4: 模型管理策略

**背景**: 不同任务需要不同能力的模型

**决策**: ModelManager 路由层

**路由策略**:
- 复杂推理: Claude 3.5 Sonnet / GPT-4
- 标准生成: GPT-3.5 Turbo
- 嵌入任务: text-embedding-3-small
- 敏感数据: 本地 Llama 3 (规划中)

**理由**:
- 成本与效果的平衡
- 单一模型故障时有降级方案
- 易于扩展新模型

### 决策 5: 数据模型重构

**背景**: 旧模型过于分散，存在冗余

**决策**: 合并相似模型，简化架构

**重构内容**:
- TestCase + TestSuite → Test (type 区分)
- Bug → Issue (扩展类型)
- Knowledge + Page → Asset (type 区分)
- Webhook → Integration (扩展类型)

**理由**:
- 减少模型数量 (26 → 14)
- 统一接口，降低复杂度
- 更好的扩展性
